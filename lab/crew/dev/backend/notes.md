### Платёжные системы — модуль оплаты на бэке
- Правило: оплата на сайте — отдельный модуль `internal/payments` за общим интерфейсом (создать платёж, проверить статус, вернуть деньги), под ним — адаптер конкретной системы (ЮKassa, CloudPayments, Т-Банк, Robokassa; за рубежом — Stripe). Статус оплаты — только по уведомлению (webhook) от системы с проверкой подписи, а не по возврату посетителя на сайт; повторные уведомления не создают двойных заказов (идемпотентность); сначала всё в тестовом режиме системы; для России — онлайн-чеки (54-ФЗ) через кассу самой платёжной системы.
- Почему: без проверки уведомлений заказ можно «оплатить» подделкой; без идемпотентности — двойные списания и заказы; смена системы не должна переписывать магазин.
- Куда: prod/crew/dev/backend/MEMORY.md (+ tech-lead — модуль в архитектуре)
- Источник: владелец (подключение платёжных систем), формулировка — агент
- Подтверждения: —
- Статус: в проде (2026-10-14)

## «Старт» в боте без кода — понятный ответ владельцу
- Правило: если бот ещё не привязан к владельцу и кто-то жмёт «Старт» без кода, отвечать «Это бот кофейни… Владельцу —
  подключите в кабинете → Уведомления»; иначе владелец думает, что подключил, а chat_id не сохранён.

## 2026-10-23 · почта и https в контейнере на бесплатном Render (ai-studio)
- **Источник:** агент (проект ai-studio).
- **Что:** коды входа не уходили: SMTP на бесплатном Render закрыт, а в `node:22-slim` нет корневых сертификатов —
  Go-API не мог открыть ни один https (ЮKassa, Telegram, почта). Решение: отправка через API почтового сервиса по HTTPS
  (Resend), в итоговый образ копировать `/etc/ssl/certs/ca-certificates.crt`.
- **Правило-кандидат:** в любом slim/distroless образе с исходящими https — сертификаты в образ; на бесплатном хостинге —
  почта только по HTTP-API сервиса. После выкладки — отправить тестовое письмо и проверить статус «delivered».
- **Куда:** prod/crew/dev/backend/MEMORY.md, prod/common/howto/notifications.md.
