# Предложение: полный цикл разработки — Figma → фронт → бэк → тесты

Статус: **предложено владельцу, ждёт «да»**. После «да» — перенос в `prod/` через `promote`
(новые роли, память ролей, агенты), по одному коммиту на роль.

Решение владельца (2026-10-14): после дизайна команда пишет фронт и бэк для всех сайтов;
фронт полностью повторяет макет из Figma; бэк полностью работает и покрыт тестами;
тестировщики ведут полный цикл; бэк — в приоритете Go; базы данных — подходящие, с расчётом
на то, что сайты будут расти.

---

## 1. Стек

| Слой | Выбор | Почему |
|---|---|---|
| Фронт | **Astro + TypeScript + Tailwind CSS**; интерактивные части — **React**-острова | статика и максимальная скорость там, где не нужна интерактивность; React — только где нужен (запись, калькулятор, подбор); токены Figma ложатся в конфиг Tailwind один в один |
| Бэк | **Go** (1.24+), роутер **chi**, логирование `log/slog` | один бинарник, быстрый, мало зависимостей, простой выход на сервер; chi — тонкая надстройка над стандартной библиотекой |
| API | **REST + OpenAPI 3** — контракт пишется первым (`backend/api/openapi.yaml`) | фронт и бэк работают параллельно по одному контракту; типы для фронта генерируются (`openapi-typescript`), заготовки сервера — `oapi-codegen` |
| Основная БД | **PostgreSQL** | надёжная, связи, JSONB для гибких данных, полнотекстовый поиск, растёт вместе с сайтом |
| Доступ к БД | **sqlc** (SQL → типизированный Go) + драйвер **pgx**; миграции — **goose** | обычный SQL без «магии» ORM, ошибки ловятся при сборке, схема меняется миграциями |
| Кэш, очереди, сессии | **Redis** — только когда нужно | счётчики, ограничение частоты запросов, фоновые задачи, сессии |
| Файлы (фото, загрузки) | **S3-совместимое хранилище** (локально — MinIO) | файлы не в БД; на сервере — любое S3-совместимое |
| Окружение | **Docker Compose**: postgres, (redis, minio), backend, frontend | у каждого сайта одинаковый запуск одной командой; на сервер переезжает без переделок |
| Проверки в репозитории | **GitHub Actions**: линтеры, тесты, сборка на каждый pull request | в `main` попадает только зелёное |

Когда что из БД:
- **Сайт-визитка без данных** — только фронт (Astro статика), бэк не создаётся.
- **Есть заявки, запись, каталог, отзывы, редактируемый контент** — Go + PostgreSQL.
- **Нагрузка, ограничение частоты, фоновые рассылки** — + Redis.
- **Заказчик загружает фото/файлы** — + S3-хранилище.
- Решение фиксирует техлид в `project/architecture.md`; расширение — новыми миграциями и модулями, без переписывания.

## 2. Репозиторий клиента (`PamyatS/<клиент>`)
```
project/            бриф, ТЗ, plan, architecture.md, content, design-spec, handoff/, qa/
frontend/           Astro: src/pages, src/components, src/styles/tokens, tests/ (e2e, визуальные)
backend/
  api/openapi.yaml  контракт API
  cmd/server/       точка входа
  internal/http/    обработчики и middleware
  internal/service/ бизнес-логика
  internal/store/   доступ к БД (sqlc)
  migrations/       миграции goose
  queries/          SQL для sqlc
docker-compose.yml  локальный запуск
Makefile            make dev / test / lint / e2e
.github/workflows/  CI
```
Ветки: `main` — принятое и согласованное; работа — в ветках `feat/<задача>` → pull request →
ревью техлида → зелёный CI → слияние.

## 4. Циклы по отделам

### 4.1 Управление (менеджер, продюсер)
1. Менеджер: знакомство → маршрут → бриф (или аудитор) → «всё верно?».
2. Продюсер: `plan.md` — нужен ли бэкенд, какие модули, какие роли, что параллельно, ворота.
3. Менеджер на каждом этапе: задача руководителю → приёмка по `acceptance.md` → показ → «ок» или правки.
4. Менеджер на сдаче: всё зелёное, заказчик принял, итоговый пакет.

### 4.2 Клиентский отдел (аналитик ★, маркетолог)
1. Маркетолог: клиенты, конкуренты, предложение, путь к заявке → `research.md`.
2. Аналитик: ТЗ — блоки и **функции**: что посетитель может сделать (оставить заявку, записаться,
   выбрать товар), что заказчик должен видеть и менять (заявки, контент, расписание).
3. Аналитик: для каждой функции — пользовательский сценарий «кто → что делает → что получает»
   и критерии приёмки (по ним потом пишутся тесты).
4. Аналитик: что может понадобиться позже (рост) — в раздел «Развитие», чтобы архитектура это не закрыла.
5. Приёмка менеджером → ТЗ простыми словами заказчику → «ок».

### 4.3 Дизайн (арт-директор ★, UX, UI, бренд, моушн, фоторедактор) — **Figma — источник правды**
1. Арт-директор: 2–3 направления стиля (палитра, шрифты, референс) → заказчик выбирает.
   *Эскиз кодом — по желанию, только для быстрого первого показа.*
2. UX: вайрфрейм в Figma — все страницы и блоки, Mobile 375 → Desktop 1440, путь к заявке.
3. Бренд и фоторедактор — параллельно: логотип, палитра, фото/видео.
4. UI: макет в Figma строго на **переменных** (цвета, шрифты, отступы, радиусы) и **компонентах**
   с auto layout; ширины 375 / 768 / 1440; **все состояния**: наведение, фокус, нажатие, ошибка,
   пусто, загрузка, успех формы; реальные тексты из `content.md`.
5. Моушн: анимации — прототип в Figma + `design/motion.md` (что, когда, длительность, кривая).
6. Арт-директор — приёмка «готово к разработке»: всё на переменных и компонентах, понятные имена
   слоёв, нет «висящих» значений, ассеты экспортируемы, состояния и адаптив на месте.
7. Менеджер → заказчик → «ок» на макет. Скриншоты согласованного — `design/approved/`.
8. Арт-директор: `project/design-spec.md` — ссылки на фреймы, список токенов, ассеты, анимации,
   «чем отличаются 375 и 1440». Это вход для фронта.

### 4.4 Контент (шеф-редактор ★, копирайтер, SEO, переводчик)
1. Копирайтер: тексты по блокам ТЗ → 2. SEO: title, description, заголовки, alt, разметка →
3. Шеф-редактор: приёмка → 4. заказчик «ок» → 5. UI вставляет тексты в макет →
6. Переводчик — после согласования основных.
Тексты для фронта — в `project/content.md` (и/или файлы контента в `frontend/src/content`), без правки руками в коде.

### 4.5 Разработка (техлид ★, фронтенд, бэкенд, перенос)
**0. Архитектура (техлид)** → `project/architecture.md`:
страницы и компоненты фронта; модули бэка; сущности БД и связи; нужен ли Redis/S3; контракт
`backend/api/openapi.yaml`; что заложено на рост. Вместе с QA-лидом — тест-план (см. 4.6).

**1. Каркас (техлид)**: репозиторий по заготовке студии, docker-compose, Makefile, CI, линтеры.

**2. Параллельно, по контракту:**

| Фронтенд | Бэкенд |
|---|---|
| а) токены из переменных Figma → `tailwind.config` / `tokens.css` | а) миграции схемы БД (goose) |
| б) компоненты один к одному с компонентами Figma, все состояния | б) SQL-запросы → sqlc → слой `store` |
| в) страницы 375 → 768 → 1440 по `design-spec.md`, контент из `content.md` | в) бизнес-логика `service` с модульными тестами |
| г) анимации по `motion.md` | г) обработчики по OpenAPI, валидация входа, понятные ошибки |
| д) запросы к API через сгенерированные типы; пока бэк не готов — заглушки по контракту | д) интеграционные тесты на настоящей PostgreSQL |
| е) сам сверяет скриншоты с фреймами Figma | е) логирование, конфиг из переменных окружения |

**3. Сборка вместе**: фронт подключается к настоящему API, сквозная проверка сценариев из ТЗ.

**4. Каждая задача** — ветка → pull request → ревью техлида (по чек-листу) → CI зелёный → слияние.

**5. Круг с качеством**: QA и автотесты находят → разработчик чинит → повторная проверка (до 3 кругов).

**Готово (разработка), когда:**
- визуальные тесты сходятся с макетом Figma на 375/768/1440 в пределах порога (п. 4.6) и UI-дизайнер подтвердил «как в макете»;
- все сценарии из ТЗ работают сквозь фронт → API → БД;
- покрытие бэка тестами ≥ 80% по `service` и `store`, CI зелёный;
- `docker compose up` поднимает сайт с нуля, миграции применяются;
- нет секретов в коде, `README` объясняет запуск.

### 4.6 Качество (QA-лид ★, QA, автотесты, скорость, безопасность, юрист)
**0. Тест-план (QA-лид + техлид, до начала разработки)** — `project/qa/test-plan.md`:
сценарии из ТЗ → какие тесты их покрывают; ширины и браузеры; что считается «блокирующим».

**1. Автотесты (`qa-automation`)**, всё запускается в CI:
| Уровень | Чем | Что |
|---|---|---|
| Модульные (бэк) | `go test` | бизнес-логика; пишет бэкенд, автотесты проверяют полноту |
| Интеграционные (бэк) | `go test` + testcontainers (настоящая PostgreSQL) | запросы, миграции, транзакции |
| Контрактные (API) | проверка ответов по `openapi.yaml` | API отвечает ровно как в контракте, ошибки — в описанном формате |
| E2E | Playwright | сценарии из ТЗ глазами посетителя: заявка дошла в БД, запись создалась, ошибки показаны |
| Визуальные | Playwright: скриншоты страниц vs экспорт фреймов Figma на 375/768/1440 | расхождение с макетом; порог по умолчанию — до 2% пикселей; всё выше — к UI-дизайнеру и фронту |
| Кроссбраузерные | Playwright: Chromium, WebKit (Safari), Firefox | одинаково работает и выглядит |

**2. Ручная проверка (`qa`)**: исследовательское тестирование, реальные сценарии, края
(пустые поля, длинные тексты, медленная сеть, двойной клик по кнопке), консоль, видео и скриншоты показа.

**3. Скорость (`performance`)**: Lighthouse мобильный ≥ 90; вес картинок и видео; ответ API — p95 < 200 мс
на лёгкой нагрузке; индексы в БД под частые запросы.

**4. Безопасность (`security`)**: проверка входных данных и формы (без SQL-инъекций — только
параметризованные запросы sqlc), ограничение частоты для форм, CORS, заголовки безопасности,
секреты только в окружении, проверка зависимостей (`govulncheck`, `npm audit`), персональные данные —
минимум и защищены.

**5. Юрист (`legal`)**: закон ниши, согласие на обработку персональных данных у форм, политика, лицензии фото.

**6. Итог (QA-лид)**: «чисто» = все автотесты зелёные, блокирующих ошибок нет, визуальное совпадение
подтверждено, отчёты скорости/безопасности/юриста без блокирующего → видео и скриншоты → менеджеру.
