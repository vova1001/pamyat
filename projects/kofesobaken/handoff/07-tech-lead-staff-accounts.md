# 07 · tech-lead · администратор и сотрудники в кабинете

## Задача (пишет менеджер)
- Цель: заказчик: «кабинет — для меня и работников, не для гостей; сделай мне аккаунт администратора, чтобы я создавал
  работников и выдавал им данные для входа; без логина и пароля войти нельзя».
- Решение (по умолчанию, заказчику сообщено):
  - роли: **администратор** (всё + раздел «Сотрудники», «Фото и тексты», «Уведомления») и **сотрудник**
    (брони, заказы, мероприятия и записавшиеся, меню);
  - первый вход: администратор — vovaoleshko05@mail.ru; пароль он придумывает сам на первом экране
    (одноразовая ссылка/код настройки из лога сервера или `ADMIN_PASSWORD` из `.env` — как удобнее, но пароль
    нигде не хранится открыто и не пересылается);
  - администратор создаёт сотрудника: имя, почта, временный пароль (вводит сам и передаёт работнику);
    при первом входе сотрудник обязан сменить пароль; администратор может отключить сотрудника и сбросить пароль;
  - все разделы кабинета и `/api/admin/*` — только после входа, права проверяются на сервере по роли;
    отключённый сотрудник выходит из всех сессий; ограничение частоты входа уже есть — проверить.
- Входные файлы: `architecture.md`, `backend/` (таблицы `admins`, `sessions`), `frontend/` (кабинет), эскиз
  раздела в превью `preview/admin.html` (раздел «Сотрудники» — для вида).
- Что сдать: миграция, API по контракту, раздел «Сотрудники» в стиле кабинета, тесты (роли, отключение, смена
  пароля, доступ без входа = 401), e2e.
- Границы: остальное не трогать; секретов в коде нет.
- Готово, когда: без входа кабинет и API закрыты; сотрудник не видит админских разделов и не может вызвать их API;
  тесты зелёные.

## Отчёт (пишет исполнитель)
- Сделано: роли `admin`/`staff` в кабинете; все `/api/admin/*` — только после входа, права проверяет сервер (без входа —
  401, сотрудник в админском — 403, с временным паролем — 403 до смены). Первый вход администратора — одноразовая
  ссылка из лога (`/admin#setup/<код>`, 72 ч, в БД только хэш); `ADMIN_PASSWORD` — лишь первый пароль, сменённый
  не сбрасывается; забыл — `docker compose exec backend server admin-link`. Раздел «Сотрудники» по эскизу превью:
  создать вход (имя, почта, временный пароль, роль), «Новый пароль», «Отключить/Включить», «это вы». Сотрудник при
  первом входе обязан сменить пароль; отключение и сброс закрывают все его сессии. Себя изменить нельзя.
- Ограничение частоты входа проверено — была дыра: chi `RealIP` доверял `True-Client-IP`/`X-Forwarded-For` от
  посетителя, nginx их не перезаписывает → лимит обходился подменой заголовка. Исправлено: адрес — только из
  `X-Real-IP` от nginx; добавлен лимит на почту (20 неверных за 15 мин с любых адресов). Есть тест.
- Проверка: `make test` зелёный (покрытие 87%), миграция up → down → up на данных; e2e 15/15 + первый вход по ссылке
  на чистом стенде; скриншоты 390/1440 сверены с эскизом.
- Файлы: `backend/migrations/00002_staff.sql`, `backend/queries/{auth,staff}.sql`, `backend/internal/service/{auth,staff,bootstrap}.go`,
  `backend/internal/httpapi/{server,handlers}.go`, `backend/cmd/server/main.go`, `backend/api/openapi.yaml`,
  тесты `backend/internal/{service/service_test,httpapi/api_test}.go`; `frontend/src/pages/admin.astro`,
  `frontend/src/scripts/admin.ts`, `frontend/src/styles/admin.css`, `frontend/tests/e2e/staff.spec.ts`;
  `README.md`, `architecture.md`, `.env.example`.
- Вопросы к заказчику: нет.
- Сверх задачи, на одобрение:
  1. Выбор роли «Администратор» при создании входа (так в эскизе) — можно завести второго администратора.
  2. Лимит неверных паролей на одну почту и исправление подмены адреса (см. выше).
- Проверить в первую очередь: на сервере (Render/Cloud.ru) `ADMIN_PASSWORD` пустой, ссылка берётся из лога backend
  (`grep link`); адрес в ссылке — из `PUBLIC_URL`, его нужно задать боевым.
- Команда: отдельных агентов (backend, frontend, qa) запустить в этой сессии нельзя — инструмента нет; сделал сам и
  проверил тестами и скриншотами.
