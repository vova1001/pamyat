# Архитектура: КофеСобакен

Сайт кофейни + кабинет администратора и сотрудников. Нагрузка малая: ~1 бронь в день, десятки заказов, единицы мероприятий в месяц.

## Схема
```
браузер ──► web (nginx :8000)
              ├─ /            → frontend (Astro, рендер на сервере :4321) ──► backend /api/site
              ├─ /admin       → frontend (страница кабинета; данные — из браузера через /api/admin)
              ├─ /pay/<id>    → frontend (страница тестовой оплаты — заглушка платёжной системы)
              ├─ /api, /uploads, /healthz → backend (Go :8080) ──► db (PostgreSQL 16)
```
Один адрес для сайта и API — cookie кабинета без CORS. Всё в `docker-compose.yml`.
Бесплатный старт на Render — те же части в одном образе (`deploy/render/Dockerfile`, nginx на `$PORT`), база Neon,
фото в PostgreSQL; `render.yaml`, инструкция — `deploy/render.md`.

## Стек и отступления от стандарта (с причиной)
| Слой | Выбор |
|---|---|
| Фронт | Astro 7 + TypeScript, `output: server` (@astrojs/node) — правки из кабинета видны гостям сразу, без пересборки |
| Стили | **CSS из согласованного эскиза без изменений** (`frontend/src/styles/site.css`, `admin.css`), дополнения — в конце файлов. Причина: источник вида — эскиз кодом (Figma не было), перевод в Tailwind дал бы расхождения с согласованным видом. Токены — CSS-переменные эскиза (`--cream`, `--tomato`, …) |
| Интерактив | обычные модули TypeScript (`src/scripts/site.ts`, `admin.ts`) — логика эскиза перенесена как есть; React-острова не нужны |
| Бэк | Go 1.24, chi, `log/slog` (JSON), pgx + sqlc, goose (миграции встроены в бинарник, применяются при старте) |
| Контракт | `backend/api/openapi.yaml`; типы фронта — `openapi-typescript` (`src/lib/api.gen.ts`). Обработчики Go написаны по контракту вручную (без oapi-codegen) — контракт небольшой, проверяется тестами API |
| Redis | не нужен: нагрузка малая; ограничение частоты форм и входа — в памяти процесса (один сервер). При нескольких серверах — перенести в Redis |
| Фото | интерфейс `media.Store` (`backend/internal/media`), выбор — `MEDIA_STORE`: `disk` — том `uploads` (docker compose), `postgres` — таблица `media` (хостинг без диска, Render). Объём — десятки фото. Переезд в S3 — ещё одна реализация `Store` |

## Модули бэка (`backend/internal/`)
- `service` — вся логика: меню, заказы, брони, мероприятия и записи, тексты сайта, настройки, уведомления, вход, сотрудники.
- `store` — код sqlc из `queries/*.sql` (только параметризованные запросы).
- `payments` — интерфейс `Provider` (создать платёж, разобрать уведомление с проверкой подлинности, вернуть деньги). `TestProvider` — тестовая страница оплаты; `YooKassa` — ЮKassa API v3 (`PAYMENT_PROVIDER=yookassa`): redirect-оплата, `Idempotence-Key`, уведомления проверяются повторным запросом к API, возврат при отмене брони/заказа, статус по API при возврате гостя (`Checker`). Чек 54-ФЗ через ЮKassa — переключатель `YOOKASSA_RECEIPT` (самозанятый — выключен).
- `notify` — интерфейс `Channel` (почта, Telegram): `Resend` (HTTP API, `RESEND_API_KEY`), `Telegram` (Bot API,
  `TELEGRAM_BOT_TOKEN`); без ключа — `LogChannel` (сообщение в лог).
- `httpapi` — роутер и обработчики, единый формат ошибки, ограничение частоты, cookie-сессии кабинета, проверка роли.

## Данные (`backend/migrations/00001_init.sql`)
| Таблица | Что | Связи |
|---|---|---|
| `admins`, `sessions` | входы в кабинет: имя, почта, роль `admin`/`staff`, включён ли, «сменить временный пароль», хэш одноразовой ссылки первого входа (миграция `00002_staff.sql`); пароль — bcrypt; сессии (в БД только хэш токена, 30 дней) | sessions → admins (CASCADE) |
| `menu_items` | позиции меню: цена в копейках, раздел, фото, «показывать», «фирменный» | |
| `orders`, `order_items` | заказ с собой/доставка; строки заказа с ценой на момент заказа | items → orders, → menu_items (SET NULL) |
| `bookings` | бронь: дата, время, гостей, с собакой, предоплата 500 ₽ | |
| `events`, `event_signups` | мероприятие (черновик/опубликовано, мест, цена); записи (держат место 20 мин на время оплаты) | signups → events (CASCADE) |
| `payments` | платёж на бронь/заказ/запись; статус меняется **только по уведомлению** платёжной системы | kind + target_id |
| `settings` | JSON: тексты и фото сайта, условия доставки, настройки уведомлений | |
| `notifications` | журнал отправленного (канал, кому, текст, успех) | |
| `media` | фото из кабинета, если `MEDIA_STORE=postgres` (миграция `00003_media.sql`) | |
| `questions` | вопросы гостей (миграция `00005_questions.sql`): откуда (сайт/бот), имя, почта или @ник, текст, чат и сообщение гостя в Telegram, id сообщения в чате владелицы (реплай = ответ), ответ и как ушёл; хранятся 1 год | уникальность (чат, сообщение) — без дублей при повторном getUpdates |

Статусы: бронь `awaiting_payment → new → confirmed / cancelled`; заказ `awaiting_payment → new → done / cancelled`;
запись `awaiting_payment → confirmed` (бесплатная — сразу `confirmed`). Неоплаченное в кабинете не показывается.
Деньги — целые копейки; время — UTC; дата и время брони/мероприятия — местные (Europe/Moscow).

## Оплата (сейчас — тестовая заглушка)
1. Гость оформляет → backend создаёт бронь/заказ/запись + платёж `pending` → ссылка `/pay/<id>`.
2. Страница `/pay/<id>` (вместо страницы платёжной системы): «Оплатить» → заглушка шлёт **подписанное уведомление**
   (HMAC-SHA256, `X-Signature`) на `/api/payments/webhook` — как настоящая система.
3. Webhook: проверка подписи, сверка суммы и платежа, повторное уведомление ничего не меняет → оплачено →
   уведомления владельцу. Возврат гостя на сайт (`/?payment=<id>`) — только показ результата, не доказательство оплаты.
4. Отмена брони/заказа в кабинете — возврат денег через `Provider.Refund`.
Подключение настоящей системы (шаг регистраций): новый адаптер в `internal/payments` + выбор в `main.go`;
чеки 54-ФЗ — через кассу системы. Остальной код не меняется.

## Уведомления
Новая бронь, заказ, запись, «мест нет», проверочное — в почту (если включена) и Telegram (если подключён);
каждое сообщение — в журнал `notifications` (виден в кабинете → «Уведомления»). Ключа нет — канал пишет в лог.
- Почта — Resend HTTP API: простое HTML-письмо (что пришло, имя, телефон ссылкой, дата/время, кнопка в кабинет).
- Telegram — Bot API без вебхука (бесплатный Render засыпает): «Подключить Telegram» → ссылка
  `t.me/<бот>?start=<код>` (30 минут, в базе хэш, ключ `telegram_link` в `settings`) → кабинет раз в 3 секунды
  зовёт `/admin/telegram/check` → сервер читает `getUpdates`, находит `/start <код>`, сохраняет `chat_id`.
  Кнопки: «Позвонить» (`/api/call/<номер>` → `tel:` — Telegram не принимает `tel:` в кнопках) и «Открыть кабинет»;
  кнопки — только на https-адресе сайта.
- «Забыли пароль?» (`/admin/forgot`) — письмо со ссылкой `/admin#setup/<код>` на 1 час, администратору и сотруднику;
  ответ одинаковый, есть почта или нет; без `RESEND_API_KEY` — подсказка «обратитесь к администратору».
- Ссылка первого входа администратора при перезапуске не перевыпускается, пока действует (72 часа);
  новая — `server admin-link` или `ADMIN_LINK_ON_START`. С `RESEND_API_KEY` она приходит и на `ADMIN_EMAIL`.

## Вопросы гостей
- Сайт: плавающая кнопка «Задать вопрос» (`components/site/Ask.astro`) → `POST /api/questions` (5 в час с адреса,
  скрытое поле-ловушка для ботов). Ответ — на почту или в Telegram по нику.
- Бот: `RunTelegram` — фоновый длинный опрос `getUpdates` (25 с), offset в `settings.telegram_offset`. Один обработчик
  (`service/questions.go`, `handleUpdate`): «/start <код>» — подключение владелицы; сообщение из её чата реплаем на
  вопрос — ответ гостю; сообщение гостя — вопрос (в кабинет, владелице в Telegram с запоминанием message_id, на почту).
  Кабинет при подключении только спрашивает статус (`/admin/telegram/check`), пока опрос идёт.
- Ответ: из Telegram реплаем или из кабинета (`POST /admin/questions/{id}/answer`): вопрос из бота — ботом реплаем на
  сообщение гостя; вопрос с почтой — письмом с сайта, только если `MAIL_DOMAIN_VERIFIED=true` (иначе `mailto:` из
  кабинета и Reply-To = почта гостя в письме владелице); ник из формы — владелица пишет сама (`t.me/<ник>`), отметка
  «отвечено». Раздел «Вопросы» — администратору и сотрудникам.

## Кабинет: роли и вход
| Роль | Разделы и API |
|---|---|
| `admin` | всё + «Фото и тексты» (`/admin/content`, `/admin/settings`), «Уведомления» (`/admin/notify/*`, `/admin/telegram/*`, `/admin/notifications`), «Сотрудники» (`/admin/staff*`) |
| `staff` | брони, заказы, вопросы гостей, меню, мероприятия и записавшиеся, загрузка фото к ним |

- Права проверяет сервер (группы маршрутов в `httpapi/server.go`): без входа — 401, не та роль — 403, вход с временным
  паролем — 403 `password_change_required` на всё, кроме `/admin/me` и `/admin/password`. Кабинет только прячет разделы.
- Администратор из `ADMIN_EMAIL`: пароль задаёт сам по одноразовой ссылке из лога (`/admin#setup/<код>`, 72 часа, в БД —
  хэш кода). `ADMIN_PASSWORD` — только первый пароль. Забыл — `server admin-link`.
- Сотрудника (или второго администратора) создаёт администратор: почта + временный пароль → при первом входе обязательная
  смена. Отключение и сброс пароля закрывают все сессии этого человека; отключённый не входит. Себя изменить нельзя —
  в кабинете всегда остаётся администратор. Смена своего пароля закрывает остальные сессии.
- «Профиль» (все роли, `#profile`): своя почта (`POST /admin/email`, нужен текущий пароль, почта уникальна — иначе 409)
  и пароль (`POST /admin/password`, текущий + новый ≥ 8). Неверный текущий пароль — 403 `wrong_password`, считается
  как неверный вход (тот же лимит). После смены — остальные сессии закрываются, письмо на прежнюю почту (если почта
  подключена). Прежние почты — в `admins.former_emails`: старый `ADMIN_EMAIL` в окружении не создаёт второй вход,
  `admin-link` по нему находит администратора под новой почтой.

## Безопасность
Секреты — только в окружении (`.env`, в репозитории — `.env.example` без значений). Пароль — bcrypt, от 8 символов; при неверном
пароле — 8 попыток за 15 минут с адреса и 20 за 15 минут на одну почту (с любых адресов). Адрес посетителя — только из
`X-Real-IP`, который ставит наш nginx; `True-Client-IP` / `X-Forwarded-For` от посетителя не учитываются. Формы — 10 оформлений в минуту с адреса. Изменения в API — только JSON
(простая чужая форма не пройдёт) + cookie `SameSite=Lax`, `HttpOnly`. Фото — только JPG/PNG/WebP по содержимому, до 8 МБ.
Ошибки наружу — без внутренностей.

## Развитие
- Настоящие оплата и уведомления — адаптеры (см. выше).
- Восстановление пароля по почте (письмо со ссылкой) — после подключения SMTP; механизм ссылок уже есть.
- Напоминания записавшимся — новый модуль поверх `notifications` и планировщика.
- Проверка адреса доставки по радиусу (геокодер) — сейчас радиус только показывается гостю.
- Несколько серверов — ограничения частоты в Redis, фото в S3.
