# Как устроена архитектура

Подробная инструкция: как работает студия из агентов, как устроена память, как мы обучаем
и как знания попадают в прод. Железные правила — `RULES.md`.

---

## 1. Главная идея: две одинаковые цепочки

```
┌─────────────────────────── prod/ ───────────────────────────┐
│  ПРОДУКТ. Только исполнение. Едет в сервис к заказчикам.     │
│  Чистые правила, без истории и без следов обучения.          │
└─────────────────────────────▲────────────────────────────────┘
                              │  только отфильтрованное
                              │  и только после «да» владельца
┌─────────────────────────── lab/ ────────────────────────────┐
│  ОБУЧЕНИЕ. Зеркало prod/ + всё вокруг: черновики каждой      │
│  роли, разговоры с владельцем, идеи, ошибки, отложенное.     │
└─────────────────────────────────────────────────────────────┘
```

- **`prod/`** — то, что исполняется. Агент читает минимум текста и сразу работает правильно.
- **`lab/`** — то, где учимся. Тут можно спорить, ошибаться, копить наблюдения.
- Устройство одинаковое: у каждой роли в проде есть «двойник» в лаборатории.
  Знание растёт в лаборатории и, проверенное, переезжает в прод.

## 2. Прод: студия из команды агентов

### Кто есть кто
```
                       ЗАКАЗЧИК
                          ⇅  (только менеджер говорит с заказчиком)
             МЕНЕДЖЕР ПРОЕКТА — prod/CLAUDE.md
                          │   продюсер — план: кого звать, в каком порядке
   ┌──────────┬────────┼─────────┬──────────┬───────────┬───────────┬────────────┐
 КЛИЕНТСК.  РАЗБОР   ДИЗАЙН    КОНТЕНТ    РАЗРАБОТКА  КАЧЕСТВО    ИНФРАСТРУКТУРА
 аналитик★  аудитор  арт-дир.★ шеф-ред.★  техлид★     руков.★     devops★
 маркетолог          UX, UI,   копирайтер фронтенд    QA          сисадмин
                     бренд,    SEO        бэкенд      автотесты   сервисы
                     моушн,    переводчик перенос     скорость
                     фоторед.                         безопасность
                                                      юрист
                                    ★ руководитель отдела
```

| Отдел | Роль | Агент | Память |
|---|---|---|---|
| Управление | менеджер проекта (главный) | — (это `prod/CLAUDE.md`) | `crew/management/manager/` |
| | продюсер | `producer` | `crew/management/producer/` |
| Клиентский | аналитик ★ | `analyst` | `crew/client/analyst/` |
| | маркетолог | `marketer` | `crew/client/marketer/` |
| Разбор | аудитор | `auditor` | `crew/audit/auditor/` |
| Дизайн | арт-директор ★ | `art-director` | `crew/design/art-director/` |
| | UX-проектировщик, UI-, бренд-, моушн-дизайнер, фоторедактор | `ux-designer`, `ui-designer`, `brand-designer`, `motion-designer`, `photo-editor` | `crew/design/<роль>/` |
| Контент | шеф-редактор ★ | `chief-editor` | `crew/content/chief-editor/` |
| | копирайтер, SEO, переводчик | `copywriter`, `seo`, `translator` | `crew/content/<роль>/` |
| Разработка | техлид ★ | `tech-lead` | `crew/dev/tech-lead/` |
| | фронтенд, бэкенд, перенос | `frontend`, `backend`, `migration` | `crew/dev/<роль>/` |
| Качество | руководитель ★ | `qa-lead` | `crew/quality/qa-lead/` |
| | QA, автотесты, скорость и доступность, безопасность, юрист | `qa`, `qa-automation`, `performance`, `security`, `legal` | `crew/quality/<роль>/` |
| Инфраструктура | devops ★ | `devops` | `crew/infra/devops/` |
| | сисадмин, менеджер по сервисам | `sysadmin`, `services-manager` | `crew/infra/<роль>/` |

Все пути — внутри `prod/`.

### Из чего состоит одна роль
```
prod/.claude/agents/design/ui-designer.md   ← КТО: инструкция агента (роль, от кого задачи,
                                               кому сдаёт, какие инструменты разрешены)
prod/crew/design/ui-designer/MEMORY.md      ← ЧТО ЗНАЕТ: стандарты роли, правила по опыту
prod/crew/design/ui-designer/figma.md       ← доп. файлы памяти роли
lab/crew/design/ui-designer/notes.md        ← ЧЕМУ УЧИТСЯ: черновики (в лаборатории)
```
Каждый агент перед работой читает: `common/` (общее для всех) → свою память → файл задачи.
`CLAUDE.md` агенты не получают (настройка `omitClaudeMd`), чтобы не путать свою роль с менеджером.

### Слои памяти прода
| Слой | Что | Кто читает |
|---|---|---|
| `CLAUDE.md` | менеджер: рамки, заказчик главный, команда, маршруты, этапы | менеджер |
| `.claude/agents/` | инструкции 27 агентов по 8 отделам | каждый — свою |
| `crew/<отдел>/<роль>/` | память каждой роли | своя роль (+ руководитель для приёмки) |
| `common/` | полный цикл шаг за шагом (`cycle.md`), стандарты, передача задач, безопасность, ошибки | все |
| `niches/` | особенности ниш (вино…) | все, если есть ниша заказчика |
| `components/` | проверенные макеты | дизайн, разработка |
| `references/` | база референсов — для идей, не для копирования | дизайн |
| `.claude/skills/` | процедуры: `new-project`, `show-result` | менеджер, QA |

### Как идёт работа по цепочке
1. **Менеджер** знакомится с заказчиком, понимает его «кривые» просьбы, ведёт бриф
   (или зовёт **аудитора**, если сайт уже есть).
2. **Продюсер** пишет `plan.md`: какие роли нужны именно этому проекту, порядок, что параллельно.
3. Менеджер ставит задачу **руководителю отдела** — файлом в `projects/<имя>/handoff/`.
4. Руководитель раздаёт подзадачи **своим специалистам**, принимает их работу, возвращает
   с замечаниями (не больше 3 кругов) и сдаёт менеджеру готовый результат отдела.
5. Менеджер проверяет глазами заказчика и показывает ему. Заказчик согласует — следующий этап.

```
Пример: дизайн
менеджер ──задача──▶ арт-директор ──▶ UX ──▶ UI (∥ бренд, фото) ──▶ моушн
                          ◀──── приёмка, замечания, круги ────┘
менеджер ◀──эскиз── арт-директор
заказчик ◀──видео и скриншоты── менеджер  →  «ок» или правки
```

Разработка: техлид (архитектура, контракт API, каркас в Docker) → фронтенд ∥ бэкенд → ревью и автотесты
по ходу → руководитель качества (автотесты, ручной QA, скорость, безопасность, юрист) → менеджер → заказчик.
Дальше: devops (ресурсы и варианты с ценами) → менеджер по сервисам (регистрации, коды, оплата) →
сисадмин и devops (сервер, выкладка, https) → сайт работает.

### Как агенты «общаются»
Не пересказом, а **файлами**: каждая задача — файл в `handoff/` с разделами «Задача → Отчёт → Приёмка»
(формат — `prod/common/handoff.md`). Работа лежит в папке проекта, по цепочке передаются пути.
Так ничего не теряется, любой видит историю, а владелец на разборе видит, где цепочка споткнулась.

### Маршруты, этапы и полный цикл
Маршруты и этапы — `prod/CLAUDE.md`; весь цикл шаг за шагом (16 шагов, кто, что, ворота) — `prod/common/cycle.md`:
знакомство → бриф → план → ТЗ → дизайн в Figma ∥ тексты → архитектура и ресурсы (варианты с ценами) →
каркас → фронт ∥ бэк → сборка → качество → показ и правки → регистрации и оплата → запуск → сдача → сопровождение.

### Стек
Всё в Docker. Фронт — Astro + TypeScript + Tailwind (React для интерактива), повторяет Figma.
Бэк — Go + PostgreSQL (sqlc, goose), контракт OpenAPI; по нужде Redis и S3. Тесты всех уровней в CI.

### Что делает заказчик
Отвечает на вопросы, один раз вводит почту и пароль для регистраций, присылает коды подтверждения,
выбирает вариант сервера и оплачивает по ссылке — всё короткими формами до 3 предложений.

## 3. Лаборатория: где и как обучаем

### Устройство
```
lab/
  crew/<отдел>/<роль>/notes.md   ← черновики памяти КАЖДОЙ роли — зеркало prod/crew/
  crew/README.md                 ← формат записи и статусы
  talk/owner.md                  ← что известно о владельце, его решения с датами
  talk/ideas.md                  ← мысли на будущее
  talk/mistakes.md               ← ошибки агента в работе с владельцем — полный разбор
  talk/questions.md              ← открытые вопросы к владельцу
  parked/                        ← история отложенного (сервисы и запуск вернулись в прод)
  archive/                       ← старые черновики, карта переезда
  rejected.md                    ← что владелец отклонил — не предлагать снова
  changelog.md                   ← журнал всех изменений прода
  test-clients/  test-runs/      ← тестовые заказчики и прогоны
  reference-candidates/          ← кандидаты в базу референсов
projects/<имя>/                  ← реальные проекты лаборатории
```

### Цикл обучения
```
 1. РАБОТА          владелец играет заказчика, команда ведёт проект по prod/
        │
 2. ЗАМЕЧАНИЕ       «так плохо, потому что…» / агент сам видит ошибку или удачу
        │
 3. ЗАПИСЬ          сразу — в lab/crew/<роль>/notes.md той роли, чья это зона
        │           (статус «ждёт», источник, причина)
        │
 4. РАЗБОР          после проекта — skill project-retro: собрать выводы по ролям,
        │           добавить подтверждения, убрать разовое
        │
 5. ФИЛЬТР          skill promote: проверка каждой записи — прошедшие получают статус «предложено»
        │
 6. «ДА» ВЛАДЕЛЬЦА  владельцу — список «правило → роль → файл». Он отвечает: да / нет / поправь
        │           нет → lab/rejected.md
 7. ПРОД            файл роли в prod/ переписывается начисто; коммит prod:; строка в changelog
        │
 8. ПРОВЕРКА        после ~5 изменений — skill prod-test: прод-команда на тестовых заказчиках
                    → найденное снова в черновики (шаг 3)
```

### Что и куда записывается
| Что произошло | Куда |
|---|---|
| Замечание про работу роли | `lab/crew/<отдел>/<роль>/notes.md` |
| Правило для всех ролей | `lab/crew/management/manager/notes.md`, «Куда: prod/common/…» |
| Удачный блок или макет | черновик арт-директора, «Куда: prod/components/…» |
| Особенность ниши | черновик аналитика, «Куда: prod/niches/…» |
| Ошибка агента в разговоре с владельцем | `lab/talk/mistakes.md` |
| Решение владельца об устройстве студии | `lab/talk/owner.md` |
| Мысль на будущее | `lab/talk/ideas.md` |
| Вопрос владельцу | `lab/talk/questions.md` |

### Статусы записи
`ждёт` → `предложено` (прошло фильтр, показано владельцу) → `в проде (дата)` или `отклонено`.
Запись сотрудника: `ждёт одобрения владельца` — дальше так же, через «да» владельца.

### Фильтр перед предложением в прод (skill `promote`)
| Проверка | Почему |
|---|---|
| Универсально — подходит любому клиенту в такой ситуации | прод работает с разными заказчиками |
| Есть причина «потому что» | без причины правило применяют вслепую |
| Нет данных клиента | данные клиентов не покидают папку проекта |
| Нет следов лаборатории | заказчик не должен видеть кухню обучения |
| Нет противоречия с действующим правилом | иначе агент получает два взаимоисключающих указания |
| Нет дубля | дубли раздувают память и расходятся со временем |
| В памяти своей роли | каждый агент читает только своё |

## 4. Перенос в прод: только с владельцем
1. Агент проходит фильтр и показывает владельцу **короткий список**: правило → роль → файл → источник.
2. Владелец отвечает по пунктам: «да», «нет 3», «поправь 2 так-то».
3. Только после «да»: файл роли в `prod/` переписывается начисто (не дописывается в конец),
   запись в черновике → `в проде (дата)`, строка в `lab/changelog.md`, коммит `prod: <роль> — <правило>`.
4. «Нет» → `lab/rejected.md` с причиной.
5. Ничего не переносится «автоматически» — ни правило владельца, ни подтверждённое в 2+ проектах.
   Подтверждения — повод предложить, а не перенести.

## 5. Как расширять
| Что добавить | Как |
|---|---|
| Правило роли | через цикл обучения (раздел 3–4) |
| Новую роль | схема владельцу → «да» → агент `prod/.claude/agents/<отдел>/<роль>.md` + память `prod/crew/<отдел>/<роль>/MEMORY.md` + черновик `lab/crew/<отдел>/<роль>/notes.md` + строка в таблице `prod/CLAUDE.md` и этого файла |
| Новую нишу | из 1–2 проектов: черновик → «да» → `prod/niches/<ниша>.md` по `_template.md` |
| Проверенный макет | «сохрани как шаблон» → «да» → `prod/components/<название>/` с README, без данных клиента |
| Референсы | владелец отмечает номера в `lab/reference-candidates/` → `prod/references/` |
| Вернуть отложенное | решение владельца → из `lab/parked/` новой ролью по правилам выше |

## 6. Команды владельца
| Сказать | Что произойдёт |
|---|---|
| «новый проект, я играю заказчика» | команда ведёт проект с нуля по `prod/` |
| «так плохо, потому что …» | запись в черновик нужной роли |
| «стоп, режим владельца» / «продолжаем» | выйти из роли заказчика и вернуться |
| «сохрани как шаблон» | кандидат в `prod/components/` |
| «сделай разбор» | разбор проекта и список кандидатов в прод |
| «что в черновиках?» | сводка черновиков по ролям |
| «в прод: <правило>» | фильтр → показ формулировки → после «да» перенос |
| «да» / «нет 3» / «поправь 2» | решение по предложенному списку |
| «откати последнее правило» | `git revert` последнего коммита `prod:` |
| «протестируй прод на клиенте 01» | прогон прод-команды на тестовом заказчике |

## 7. В сервисе
В сервис копируется только `prod/`: менеджер — `CLAUDE.md`, агенты — `.claude/agents/`,
их память — `crew/` и `common/`. У каждого заказчика своя сессия и папка проекта.
Подробно — `service/architecture.md`.
