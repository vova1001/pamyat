# Полный цикл проекта — шаг за шагом

Один документ на всю команду: кто, что берёт, что делает, что сдаёт, кто проверяет, где ворота заказчика.
Каждый шаг — задача файлом в `project/handoff/` (`common/handoff.md`). ★ — руководитель отдела.
**[ВОРОТА]** — без «ок» заказчика дальше не идём. **[ФОРМА]** — запрос к заказчику формой или
сообщением не длиннее 3 предложений.

```
 1 Знакомство ─▶ 2 Бриф ─▶ 3 План ─▶ 4 ТЗ ─▶ 5 Дизайн ∥ 6 Тексты ─▶ 7 Архитектура и ресурсы
                                                                              │
 ┌────────────────────────────────────────────────────────────────────────────┘
 ▼
 8 Каркас ─▶ 9 Фронт ∥ Бэк ─▶ 10 Сборка вместе ─▶ 11 Качество ─▶ 12 Показ и правки ─┐
                 ▲                                    │  ошибки                      │ правки
                 └────────────────────────────────────┘◀─────────────────────────────┘
 ▼ «принято»
 13 Регистрации и оплата ─▶ 14 Запуск ─▶ 15 Сдача ─▶ 16 Сопровождение ─▶ (новая правка → шаг 12)
```

---

## 1. Знакомство — менеджер
- Приветствие, один вопрос: сайт с нуля или есть готовый (`crew/management/manager/communication.md`).
- Коротко объяснить путь и что нужно от заказчика.
- Готовый сайт → задача `auditor` (разбор: `audit.md`, рекомендация доработать/переделать) **[ВОРОТА]**.
- Skill `new-project`: репозиторий проекта и структура.

## 2. Бриф — менеджер
- Вопросы блоками по 2–3 (`brief.md` в памяти менеджера), включая блок «Данные», если у сайта будут заявки,
  запись, каталог, файлы.
- Выжимка → «всё верно?» **[ВОРОТА]** → `project/brief.md`.

## 3. План — продюсер
- Тип проекта, нужен ли бэкенд и какие модули, состав ролей, порядок, что параллельно → `project/plan.md`.

## 4. ТЗ — аналитик ★ (+ маркетолог)
1. Маркетолог: клиенты, конкуренты, предложение, путь к заявке → `research.md`.
2. Аналитик: блоки и страницы; **функции** (что делает посетитель, что видит и меняет заказчик);
   сценарии «кто → что делает → что получает» с критериями приёмки; **данные** (что хранится,
   сколько в день, как долго, файлы); «Развитие» — что может понадобиться позже.
3. Менеджер: приёмка → ТЗ простыми словами заказчику **[ВОРОТА]** → `project/tz.md`.

## 5. Дизайн в Figma — арт-директор ★ (параллельно с шагом 6)
1. Арт-директор: одно направление стиля — как хочет заказчик **[ВОРОТА: «ок» на направление]**.
2. UX: вайрфрейм всех страниц в Figma, 375 → 1440, путь к заявке.
3. Бренд-дизайнер и фоторедактор — параллельно: логотип, палитра, фото и видео.
4. UI: макет на переменных и компонентах, 375 / 768 / 1440, все состояния, реальные тексты.
5. Моушн: анимации — прототип + `design/motion.md`.
6. Арт-директор: приёмка «готово к разработке» → `project/design-spec.md`.
7. Менеджер: показ **[ВОРОТА: макет]**.

## 6. Тексты — шеф-редактор ★ (параллельно с шагом 5)
Копирайтер → SEO → шеф-редактор (приёмка) → менеджер **[ВОРОТА: тексты]** → UI вставляет тексты
в макет → переводчик (если нужен) → `project/content.md`.

## 7. Архитектура и ресурсы — техлид ★ + devops ★
1. Техлид: `project/architecture.md` — страницы и компоненты, модули бэка, сущности и связи БД,
   нужен ли Redis / файловое хранилище (S3), контракт `backend/api/openapi.yaml`, что заложено на рост.
2. QA-лид + техлид: `project/qa/test-plan.md` — какие тесты покрывают каждый сценарий ТЗ.
3. Devops: расчёт ресурсов по данным из ТЗ (`crew/infra/devops/MEMORY.md`); если данных не хватает —
   менеджер спрашивает заказчика **[ФОРМА]**.
4. Devops: один подходящий вариант сервера (и S3, если нужно) с актуальной ценой → `project/infra/options.md`.
5. Менеджер: вариант заказчику — коротко, с ценой **[ВОРОТА: «ок» на вариант и бюджет]**. Другие — только если попросит.

## 8. Каркас — техлид
До начала разработки у заказчика есть свой закрытый репозиторий в организации студии — весь код и материалы
проекта только в нём; рабочие ветки пушатся сразу, работа видна с первого дня. Каркас в нём по заготовке студии: `docker-compose.yml` (frontend, backend, postgres, при нужде redis, minio),
`Makefile`, линтеры, CI на каждый pull request. `docker compose up` поднимает пустой сайт.

## 9. Фронт ∥ бэк — фронтенд и бэкенд (ведёт техлид)
Сначала — сквозной рабочий кусок того, что заказчик явно просил, затем полная оболочка сайта; внешние сервисы
(оплата, уведомления, перевод) — заглушками за интерфейсом, подключаются на шаге 13. Превью — заказчику сразу.
| Фронтенд | Бэкенд |
|---|---|
| токены из переменных Figma → Tailwind | миграции схемы БД |
| компоненты один к одному с Figma, все состояния | SQL-запросы → sqlc → `store` |
| страницы 375 → 768 → 1440 по `design-spec.md`, контент из `content.md` | бизнес-логика `service` + модульные тесты |
| анимации по `motion.md` | обработчики по OpenAPI, проверка входа, понятные ошибки |
| запросы к API по сгенерированным типам; до готовности бэка — заглушки по контракту | интеграционные тесты на настоящей PostgreSQL |
| сам сверяет скриншоты с фреймами Figma | логи, настройки из окружения |

Перенос со старого сайта (если есть) — `migration`. Каждая задача: ветка → pull request → ревью техлида →
CI зелёный → слияние. По ходу — быстрые проверки `qa` и `qa-automation`.

## 10. Сборка вместе — техлид
Фронт подключён к настоящему API; все сценарии ТЗ проходят насквозь фронт → API → БД;
`docker compose up` с нуля поднимает рабочий сайт. Техлид сдаёт менеджеру «готово к проверке».

## 11. Качество — QA-лид ★
Параллельно: автотесты (модульные, интеграционные, контрактные, e2e, визуальные против Figma,
кроссбраузерные) · ручная проверка · скорость · безопасность · юрист.
Ошибки → файл замечаний → менеджер → техлид (или нужный отдел) → исправление → повтор.
**Возврат на шаг 9, пока не «чисто».** Итог: «чисто» + видео прокрутки и скриншоты.

## 12. Показ и правки — менеджер
Приёмка (`acceptance.md`) → показ **[ВОРОТА: сайт]** → правки нужному отделу → шаг 11 → показ.
До «принято».

## 13. Регистрации и оплата — devops ★ → services-manager
Платёжная система: заказчика просим зарегистрироваться самому (короткая инструкция формой) — дальше команда
находит в кабинете всё нужное, настраивает и подключает к сайту.
1. Менеджер: один раз — почта и пароль заказчика для регистраций **[ФОРМА]** → хранилище доступов.
2. Services-manager: регистрирует аккаунты (сервер, хранилище, адрес сайта) на заказчика;
   коды подтверждения — по одному, по мере прихода **[ФОРМА: код]**.
3. Оплата — ссылка или QR-код самого сервиса, за что и сколько **[ФОРМА: оплата]**; ждём подтверждения
   оплаты в сервисе. Запись в `project/services.md` (без паролей и кодов).

## 14. Запуск — devops ★ → sysadmin
Sysadmin: настройка сервера (обновления, доступ по ключу, firewall, Docker), резервные копии БД и файлов,
мониторинг. Devops: выкладка (`docker compose` на сервере), адрес сайта, https, проверка с телефона и компьютера.
QA-лид: короткая проверка на боевом адресе. Менеджер: **[ВОРОТА: «сайт работает»]**.

## 15. Сдача — менеджер
Ссылка на сайт; что и как можно менять (через студию); где лежит, на кого оформлено, когда продлевать —
из `services.md`; видео и скриншоты итоговой версии.

## 16. Сопровождение — менеджер
Правки → шаг 12. Продления — за 30 и за 7 дней (services-manager). Рост сайта (новый модуль,
больше данных) → шаг 4 (дополнить ТЗ) → архитектура → по циклу; ресурсы пересчитывает devops.
