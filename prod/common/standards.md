# Стандарты студии (для всех ролей)

## Принципы
1. **Результат для бизнеса, а не красота ради красоты.** Сайт нужен, чтобы клиенту звонили,
   писали и покупали. Каждый блок отвечает на вопрос «как это приближает к заявке?».
2. **Качество студии, а не конструктора.** Никаких шаблонных «Добро пожаловать на наш сайт»,
   стоковых рукопожатий и одинаковых карточек с иконками.
3. **Мобильный — первым.** Большинство посетителей малого бизнеса приходят с телефона.
4. **Не выдумывай факты.** Цены, адреса, телефоны, отзывы, лицензии, цифры — только от заказчика.
   Нет — явная пометка `[УТОЧНИТЬ: что именно]` и вопрос в отчёте.
5. **Проверяй себя до сдачи.** Каждый сдаёт работу, которую сам проверил по своим критериям.
6. **Простое решение лучше умного.** Минимум зависимостей, минимум кода, максимум скорости.
7. **Коротко и по делу.** Не заваливай собеседника стеной текста: в отчётах и сообщениях — суть и пути к файлам.
8. **Только результат.** Приоритет — дизайн и разработка. Каждое действие двигает к тому, что заказчик увидит;
   проверки, исследования и отчёты — минимально необходимые, без повторов.
9. **Один вариант.** Делаем один вариант — такой, как хочет заказчик. Альтернативы — только если он попросил.
10. **Сначала полная оболочка.** Сначала собираем работающий сайт целиком (с заглушками внешних сервисов),
    показываем, затем подключаем сервисы.

## Механики
Повторяющиеся вещи делаются по механикам `common/howto/` (как устроено, как делать, на чём спотыкаются).
Нашёл способ лучше — опиши в отчёте, механику обновят.

## Роли и границы
- С заказчиком говорит только менеджер. Остальные пишут вопросы к заказчику в отчёт.
- Каждый работает в своей зоне (см. таблицу ниже) и не правит чужой результат — пишет замечание.
- Работу не останавливаешь из-за нехватки данных: ставишь `[УТОЧНИТЬ]` и идёшь дальше.
- Проекты никогда не смешиваются. Код одного проекта не импортирует код другого.
- `crew/`, `common/`, `niches/`, `components/`, `references/` — используешь, но не меняешь.

## Репозиторий проекта и кто за что отвечает
У каждого проекта — свой закрытый репозиторий студии. Всё про проект — в нём.
```
project/
  brief.md          менеджер — ответы заказчика
  audit.md          аудитор — разбор готового сайта
  plan.md           продюсер — состав команды, порядок, что параллельно
  research.md       маркетолог — клиенты, конкуренты, предложение
  tz.md             аналитик — ТЗ: блоки, функции, данные, развитие
  design-spec.md    арт-директор — вход для фронта: фреймы, токены, ассеты, анимации
  design/           дизайн-отдел: links.md (ссылки на Figma), style.md, motion.md, approved/
  content.md        контент-отдел — все тексты сайта
  architecture.md   техлид — устройство сайта, модули, БД, рост
  infra/            devops — расчёт ресурсов, options.md (варианты с ценами), устройство сервера
  services.md       services-manager — сервисы, на кого, что оплачено, до какого числа (без паролей)
  qa/               отдел качества — test-plan.md, отчёты, show/ (видео и скриншоты)
  handoff/          задачи и отчёты между агентами (common/handoff.md)
  revisions.md      менеджер — правки: что попросили → кто сделал → что сделали
frontend/           фронтенд — Astro: src/, tests/ (e2e, визуальные)
backend/            бэкенд — Go: api/openapi.yaml, cmd/, internal/, migrations/, queries/
assets/             материалы заказчика и подобранные фото/видео (+ sources.md)
docker-compose.yml  техлид — все части проекта в Docker
Makefile            техлид — make dev / test / lint / e2e
.github/workflows/  техлид — проверки на каждый pull request
```
- Всё запускается в Docker: `docker compose up` поднимает проект с нуля — локально и на сервере.
- Ветки: `main` — принятое и согласованное; работа — `feat/<задача>` → pull request → ревью → зелёные проверки → слияние.
- Секреты — только в переменных окружения и хранилище доступов; в репозитории — `.env.example` без значений.
- У каждого сайта с формами — страница политики обработки данных и согласие у каждой формы (`crew/quality/legal/`).

## Язык и тон
- Всё, что может увидеть заказчик, — на понятном языке, без терминов и внутренней кухни.
- Внутренние файлы — по делу, без воды.
