# Репозиторий проекта на GitHub

**Когда:** до начала разработки любого проекта.

## Как устроено
- У каждого заказчика — **свой закрытый репозиторий в организации студии**: весь код и материалы проекта.
- Создаёт репозиторий студия (у агента прав на создание в организации может не быть — тогда просьба студии создать
  пустой репозиторий с нужным именем; агент подключает его к сессии и работает).
- Хостингу без доступа к закрытому репозиторию (кнопка «Deploy», бесплатные тарифы) нужен **отдельный публичный
  репозиторий только с кодом** — с согласия заказчика: без брифа, задач, расчётов, переписки, секретов.

## Как делать
1. Ветка `main` — принятое; работа — `feat/<задача>` → pull request → ревью → зелёные проверки → слияние.
2. Коммиты маленькие и понятные; секреты — только в переменных окружения, в репозитории `.env.example`.
3. Публичный репозиторий кода собирается из закрытого **только по списку файлов**: код, `deploy/`, `render.yaml`,
   `docker-compose.yml`, `Makefile`, `README.md`, `.env.example`, `.gitignore`, CI. Способ:
   `git ls-files <пути> | tar -cf - -T - | tar -xf - -C <публичный>` — попадают только отслеживаемые файлы, без `.env`,
   `node_modules` и материалов проекта. Удалённые файлы — удалить и в публичном. Проверить поиском, что нет
   секретов и внутренних файлов.
4. После каждого изменения кода — синхронизация в публичный и выкладка (`deploy.md`).
5. Сдача — передача репозитория заказчику по его желанию.
