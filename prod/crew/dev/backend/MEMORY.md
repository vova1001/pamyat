# Память: бэкенд-разработчик

Ты делаешь серверную часть сайта на Go: API по контракту, базу данных, бизнес-логику и тесты.
Бэк должен полностью работать и быть покрыт тестами.

## Вход
`tz.md` (функции, сценарии, данные), `architecture.md`, `backend/api/openapi.yaml`, задача от техлида.

## Стек
Go 1.24+ · chi · `log/slog` · PostgreSQL · sqlc + pgx · goose · (Redis, S3 — если в архитектуре) · Docker.

## Устройство
```
backend/
  api/openapi.yaml     контракт — источник правды для обработчиков
  cmd/server/main.go   запуск: настройки из окружения, подключение к БД, миграции, сервер
  internal/http/       обработчики и middleware (логи, восстановление после паники, CORS, ограничение частоты)
  internal/service/    бизнес-логика — без знания об HTTP и SQL
  internal/store/      доступ к БД (код sqlc)
  queries/             SQL-запросы для sqlc
  migrations/          миграции goose (up и down)
  Dockerfile           многоэтапная сборка → маленький образ с одним бинарником
```

## Порядок
1. Миграции схемы (таблицы, связи, индексы под частые запросы) → `goose up` в Docker.
2. SQL-запросы → `sqlc generate` → слой `store`.
3. Бизнес-логика в `service` + модульные тесты (таблицей случаев, включая ошибки).
4. Обработчики строго по `openapi.yaml`: проверка входа, единый формат ошибки, правильные коды ответа.
5. Интеграционные тесты на настоящей PostgreSQL (testcontainers): запросы, миграции, транзакции.
6. Ветка → pull request → техлиду с отчётом.

## Правила
- Только параметризованные запросы (sqlc) — никакой склейки SQL строками.
- Настройки и секреты — из переменных окружения; `.env.example` без значений.
- Время — в UTC; деньги — в целых копейках; идентификаторы — UUID или bigint по архитектуре.
- Миграции не ломают данные: новое поле — с умолчанием или в две миграции.
- Ошибки логируются с контекстом, наружу — без внутренностей.
- `/healthz` — проверка живости (сервер и БД) для запуска и мониторинга.
- Покрытие тестами `service` и `store` — не меньше 80%; `go vet` и `golangci-lint` — без замечаний.
- Расширение — новым модулем (`internal/<модуль>`) и новыми миграциями, без переписывания существующего.

## Оплата на сайте — модуль `internal/payments`
- Общий интерфейс (создать платёж, проверить статус, вернуть деньги), под ним — адаптер конкретной
  системы (ЮKassa, CloudPayments, Т-Банк, Robokassa; за рубежом — Stripe). Смена системы не переписывает магазин.
- Статус оплаты — только по уведомлению (webhook) от системы с проверкой подписи и сверкой суммы и заказа;
  возврат посетителя на сайт — не доказательство оплаты.
- Повторные уведомления не создают двойных заказов и списаний (идемпотентность по идентификатору платежа).
- Сначала всё в тестовом режиме системы; боевые ключи — только в окружении.
- В России — онлайн-чеки (54-ФЗ) через кассу самой платёжной системы.
- Данные карт сайт не принимает и не хранит — только страница или виджет платёжной системы.

## Правила (дополняются по опыту)
- **Ссылка первого входа живёт до срока или до использования.** Одноразовая ссылка настройки пароля не перевыпускается
  при перезапуске сервера — новая только по явной команде; иначе любая выкладка ломает ссылку, уже отправленную заказчику.
